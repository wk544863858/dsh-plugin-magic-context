# 全局域候选的来源问题 —— 复现检测在真实语料上是空门

> **日期**：2026-10-10 · **方法**：对共享库只读查询 + 在实测库上跑检测器 · **结论一句话**：
> 规划里 WP9 的候选来源（"同一 normalized_hash 出现在 ≥2 个项目"）在现有 1292 行 / 33 个项目上
> **命中 0 条**，且这不是实现缺陷——historian 产出的事实天然是项目绑定的。
> 因此**不再把它当来源**，改为：检测器保留为"测量"，来源换成**人工晋升**。

---

## 1. 测量（三个独立判据，方向一致）

| 判据 | 结果 |
|---|---|
| 同一 `normalized_hash` 被 ≥2 个 `project_path` 共享（active） | **0** |
| 同一 `normalized_hash` 被 ≥2 个 `project_path` 共享（含非 active） | **0** |
| `content` 完全相同且跨 ≥2 个项目 | **0** |
| `content` 前 60 字符相同且跨 ≥2 个项目 | **0** |
| 分母 | active 1292 行 · 33 个不同 `project_path` |

第 3/4 条是关键：即使完全绕开 `normalized_hash` 的算法（它是 MC 侧写的），**内容本身也不重复**。
所以"门是空的"不是 hash 算法造成的假象。

**在实测库上跑检测器的结果**（`detectGlobalCandidates`，6ms）：

```
{"hashes":0,"upserted":0,"blocked":0,"samples":0}
```

## 2. 为什么必然如此

`historian` 从**一个项目的会话**里提炼事实：文件路径、模块名、当次事故的具体证据、本项目的约定。
这类知识天然带项目坐标。跨项目复现要成立，得有两个项目独立写出**归一化后完全一致**的一句话——
在 33 个项目的规模上不发生，也没有理由随规模自然发生。

换句话说：**这不是"还没攒够数据"，而是来源选错了**。

## 3. 因此改掉了什么

| 项 | 原规划 | 现在 |
|---|---|---|
| org 候选来源 | 复现检测（≥2 项目同 hash） | **人工晋升**（人类认定某条项目记忆是组织级知识） |
| 检测器的角色 | 生产候选 | **测量**：回答"复现现在成立了吗"，一条命令可重跑 |
| 晋升对象 | 隐式（扫描产出） | 显式：记录 `source_memory_id` + `category`（schema v9 两列） |
| 批准门 | 一律要求 `distinctIdentities ≥ 2` | **分两种信号**：机器检测的一律要复现；人工晋升只需过发布前置校验 |

最后一条是这次做的设计判断：复现门的目的是**拦住机器把一次性观察变成组织真理**。
人工晋升已经是人的判断，批准是第二个人工动作——对它再套复现门等于否定人的判断。
但**发布前置校验对两者一视同仁**：凭据形状拒写、类别必须在域白名单内。

## 4. 这次的落点在哪（不碰契约）

- `src/core/global-domains.ts`：凭据扫描、复现检测（测量）、人工晋升、批准门、发布计划
- `src/dsh/command-surface.ts`：`/ctx-global promote <memoryId>`、`/ctx-global detect`
- `tests/org-domain.spec.ts`：13 用例（含"真实语料不该被误判为凭据"的负向对照——40 位 hex 遍地都是，
  规则若对它们开火等于封掉几乎所有候选）
- **以上全部只写适配器自有表**（`global_candidates` / `global_candidate_observations`）

**发布已落地（2026-10-10，WP9 / commit 70104f546）**：把批准的候选发布进共享库的域身份
（`project_path='dir:global:org'`、`scope='universe'`、`shareable=1`、`source_type='user'`），
按 `UNIQUE(project_path, category, normalized_hash)` 幂等，且发布前校验类别在域白名单内
（不在 ⇒ 结构化拒绝，而不是发布后静默不可见）。**实测库上至今未发布过任何一行**——
首次实测库发布仍要走"备份 → dry-run → 真写"。

## 5. 产品判据要重新表述

原判据是"上线 2 周内若没有任何一条 org 记忆被 ≥2 个不同项目命中，判定需求不成立"。
现在的测量更早、更根本：**来源侧就已经是 0**——不是"发布了没人用"，而是"根本没有东西可发布"。

所以真正要回答的问题变成：**这台机器上是否存在需要跨项目共享的知识？**

## 6. 若要继续做，四条路

| 方案 | 成本 | 判断 |
|---|---|---|
| **A. 停止 org 域投入** | 0 | 与测量一致。诚实选项 |
| **B. 语义复现**（embedding 近邻跨项目 ≥ 阈值） | 要 WP11 向量回填先落地；会引入阈值调参与误报治理 | 实测库里已有两个 `model_id` 的向量行，但覆盖率未知；**误报会把无关知识提升为组织真理**，代价高于漏报 |
| **C. 人工晋升**（已实现） | 已付 | 可立刻用；瓶颈是"人得先知道某条记忆值得共享" |
| **D. historian 写入时打域标签** | 改 historian 输出契约 | **值得注意**：事实**已经**由适配器写进契约（`promoteFacts` 是既有写路径），
所以加一个 `scope_hint: org` 字段**不新增写路径**。但 LLM 自己判"这是组织级"同样会误判，
需要与 C 一样的确认门 |

**建议**：先按 C 用两周，同时记录"有多少次人工晋升 / 有多少次晋升被自己否掉"。
若两周内晋升次数为 0，按 A 收掉；若晋升频繁而"发现难"，再考虑 D。

**不建议**在没有语义判据治理方案前上 B——把误报的组织真理注入所有成员项目，代价高于收益。
