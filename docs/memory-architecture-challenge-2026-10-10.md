# 记忆机制架构挑战与评估（2026-10-10）

> 口径：本文所有断言分三级——**[实测]** 当场在实测库/上游源码验证过；**[代码]** 读过代码锚点；
> **[历史]** 来自既往已归档的核实记录。未验证的不写。
> 评估对象：dsh-plugin-magic-context 全部记忆机制（召回/写入/晋升/评分/压缩/维护/检索/全局域/画像/观测）。

---

## 0. 总判

系统**能工作且防御扎实**，但今天它背着一个**消失的对手方**、一条**对中文残废的检索通道**、
五个**各自为政的同步游标**、以及一个**建立在实测为 0 的前提上的全局域子系统**。
复杂度预算已经是本插件最稀缺的资源：607 个测试守护着一组**大部分开关默认关**的功能。
下面按严重度排列，每项给证据、挑战、选项、建议。

---

## 1. P0：两个活缺陷（当场核实）

### 1.1 route-health 的 provider 粒度假抑制（我 20 分钟前引入的）

- **[实测]** 上游 `runtime-types.ts:353`：`agent/request-error` 载荷**只有 `provider: string`，没有 model**。
- **[历史]** 10-09 的额度事故本身就是反例：`provider-a/model-a` 配额死（22:28 起），
  而**同 provider** 的 `provider-a/model-b` 在 00:34 正常跑 verify——
  配额是**路线级**（provider/model），事件是 provider 级。
- **后果**：按今天的代码，那晚 model-a 的 429 会武装 `provider-a`，
  把正在 model-b 上正常工作的维护车道静默跳过 45 分钟一个周期。
- **修复方案**（一句话）：**只对"主对话当前自己的路线"生效**——
  跳过条件收紧为 `tickRoute ≡ lastSessionRoute（provider+model 都等）&& 事件.provider === tickRoute.provider`。
  未钉时的 tick 路线本来就是 lastSessionRoute（恒等成立，主场景无损）；钉子路线与主对话分歧时**永不跳过**
  （宁可多花一个秒败请求，不错杀一条活路线）。

### 1.2 search-hint 仍指向不存在的工具 `ctx_search`

- **[实测]** `search-hint.ts:34/81/164` 三处让模型去调用 `ctx_search`；注册的工具只有
  `ctx_reduce/ctx_expand/ctx_memory`。`tests/search-hint.spec.ts:52` 把坏串锁进了断言。
- **后果**：这是记忆系统**最高频的用户可见触点**（每轮首条消息 ≥24 字符即触发），
  它指示模型执行一个不可能的动作——模型照做即得到 tool-not-found 噪音。
- **修复**：三处文案 + 测试断言改为 `ctx_memory`（`action:"search"`），一个 spec 的事。
  盘点报告（#1298 缺陷①）记录于 0.4.3 时代，至今未修——**被"已知缺陷"状态麻痹了 7 个版本**。

## 2. 结构性挑战（按严重度）

### C1. 两库分治是大部分复杂度的**根因**，而它防御的对手方已经消失

- **[历史]** context.db 冻结在 v94/196 对象；"OpenCode 与 Pi 都将移除、dashboard 不留"
  ⇒ **本插件已是该库唯一读者写者**。
- **[代码]** 冻结的直接代价贯穿全部新能力：域/候选/确认队列建在适配器库再在应用层"跨库连接"（WP1）；
  共享属性要在每次 update 后手工恢复（WP4 preserveSharing）；epoch 指纹与上游算法**明知不一致也不修**
  （sha1 vs sha256、不含 share_categories）；m[0] digest 不含 content（已知缺陷⑥）也**没法修**——
  因为修它要动契约列语义。
- **挑战**：冻结从"兼容承诺"变成了"为幽灵保守的守恒定律"。五个同步游标（§C3）全部源于
  "读一个不归我管的存储"。**单写者 + ~1400 行数据的今天，一次性迁移到自有库是一个下午的工作量**；
  每多一个 WP，双轨成本就复利一次。
- **选项**：A 维持冻结（零风险，复杂度持续）；B 新写走自有库、context.db 只读退役（渐进，两库并存更复杂）；
  C **一次性迁移**：自有库收编全部数据，契约库退役为冷备份（数据量小、单写者、freeze 探测器反着用——
  验证迁移完整性）。
- **建议**：把 C 排为**下一个大版本的候选**，先做迁移演练（dry-run 全量复制 + 校验和比对），
  用数据说话再决策。冻结探测器、契约写入风控这些守卫在迁移完成后**整层退役**。

### C2. 中文检索的现实：FTS 通道对中文基本失效，向量车道不是"优化"而是"唯一语义通道"

- **[实测]** `memories_fts_config` 只有 `version=4` ⇒ **默认 unicode61 分词**。
  实测库实测：`MATCH '记忆'` 命中 **6** 行，`LIKE '%记忆%'` 命中 **34** 行（18%）；
  `MATCH '路线'` 2 行 vs 20 行（10%）。unicode61 把整个中文连续段当一个 token，
  只有恰好被标点/空格隔开的词才可命中。
- **挑战**：本库记忆**主体是中文**。这意味着：
  ① 混合检索里的 FTS 分量（权重 0.7）对中文近似随机；
  ② **向量车道（权重 0.3）实际承担了中文语义检索的全部**；
  ③ 而向量覆盖率 67.0%→64.6% **持续下滑**、回填开关默认关（待回填 525 条、前沿后 255 条从未嵌入）。
  **"回填可以慢慢来"的前提不成立——每一条未嵌入的中文记忆在语义检索里接近不可见。**
- **建议**：① 把 `memory.vectorBackfill` 的开启从"可选优化"升级为**正确性事项**（备份→开→观测覆盖率回升）；
  ② 若走 C1-C 迁移，顺手把 FTS 换成 trigram 分词（对中文子串检索即可用），向量降回"优化"定位；
  ③ 短期可给 search 的 FTS 分量对纯中文查询做 LIKE 兜底（只在自有库侧改，不碰契约）。

### C3. 五条同步游标，组合盲区是已知缺陷的产地

- **[代码/历史]** `maxMemoryId` 水位（m[1]）、`m[0] digest`（sha1(id:updated_at)，不含 content）、
  `mutation-log cursor`（memory-updates）、`epoch 指纹`（不含 share_categories）、
  `profile_watermark + profile_m0_digest`。各自有测试，**组合**上挂着已知缺陷⑥⑦⑧：
  digest 盲区（内容改写不触发）、merge 不清 embeddings/verifications、召回 SQL 无 verification 门。
- **挑战**：每条游标是一条独立的状态机义务（"promotion 纯追加不 bump epoch"这类不变量靠人记）。
  **一个由写者维护的单调 change-sequence 能坍缩全部五条**——但契约冻结不让加列（回到 C1）。
- **建议**：短期在已知缺陷⑥⑦⑧上各挂一个"是否已实际发生过"的探测（多数可能从未触发），
  用数据排优先级；根治绑 C1。

### C4. org/machine 全局域：建立在实测为 0 的前提上，且验收判据当前不可测

- **[历史/实测]** 跨项目知识复现三个独立判据**全部为 0**（#1281）；检测器保留为"测量"。
  WP9/WP10 的产品判据（"2 周内 ≥2 项目命中否则停投"）依赖的**域命中埋点不存在**（§8 C-7，
  我今晨核实）——即这条"用数据决定去留"的承诺，**数据通道本身没铺**。
- **挑战**：三个域 = 域表+成员表+候选表+观测表+确认表+发布/退役/可见性矩阵+41 个 phase C 用例，
  守护着一个**测量说不会自然发生**的进料源。唯一有真实内容且全局注入的是 user 画像（14 行）——
  而它恰好又缺跨会话门（§8 C-0，一个话多会话可自造 3 条观察晋升进所有会话）。
- **建议**：① 优先落 C-7 埋点（半天工作量），让判据可测；② org/machine 开关保持 off，
  **判据到期未达标即删除**（保留 git 历史，不留过渡层）；③ C-0 跨会话门按已给方案补上。
  这是"测量或删除"，不是"再观察观察"。

### C5. 注入的压力门 = 记忆可见性的悬崖

> **2026-10-10 10:00 落地与实测**（仪表已上线：mc-report「基线/fold(14d)」+「稀释(30d)」两行，scripts/report-dilution.mjs + score-diff.mjs）：
> - **风险 2（会话内 m[1] 峰值）实测为不存在**：14 天内基线刷新 382 次（hard 80 / soft 302，平均间隔 13m），
>   当前未折叠增量仅 memories 12 / profile 0 / mutations 1 行——fold 机制远比假设的勤快。
>   **饱和触发 fold 的泄压阀按 YAGNI 条款不做。**
> - **风险 1（稀释）实测为真且比预想严重**：近 30 天新行进入率仅 **18%**（135/765）——82% 的新记忆从未进过
>   基线窗口；top40 集中度 83%（40 行吃掉 83% 的注入份额）；**归档 0 行**——TTL archive 从未生效，
>   池子的自限减压阀是死的（local_archived 恒 0，sidecar 从未归档过任何行）。
> - **S(t) 排序离线 diff（实测库）**：现状 40 行 vs 候选 40 行，重叠 26，换出 14（退役 0）/ 换入 14——
>   换入行全部 hits≥1（被用过），换出行全部 hits=0（从未被检索）。**排序语义与设计意图一致，
>   且退役数 0 说明开关翻转不会丢任何"活"行。** 决策数据已备齐（`node scripts/score-diff.mjs`）。

- **[代码]** 召回/画像/基线刷新**只发生在 execute 带**；压力低于阈值的会话被 defer ⇒
  **零注入、零画像、零 memory-recall 事件**。
- **挑战**：对用户，记忆系统的价值是**二值且不可预测**的——同样的问题，长会话"它记得"，
  短会话"它失忆"。对评估同样不利：defer 会话里记忆命中率**结构性无法测量**（没有对照组）。
- **建议**：这是有意的权衡（省 token），但缺一个**出口**：给 defer 会话加一条
  "每 N 轮强制注入一次 m[0] 摘要（裁到 25% 预算）"的廉价保底，让可见性从悬崖变斜坡。
  实现点在 policy.ts 的 defer 分支，不动契约。

### C6. LLM 管道的成本结构：四条管线、两条功能重叠

- **[代码]** historian（全跨度重放、分块 16k、重试+cap 翻倍+修复提示）、compaction engine（同源摘要）、
  maintenance verify、profile review——今天起**四条同路线同配额池**（统一是裁决，但单点故障面也并了）。
- **[历史]** historian 是重的那条：一次 run 多 chunk × 16k 生成；47 条失败里 invalid-output 7 条
  靠重试翻倍救回（有效，保留），但**全跨度重放**意味着 span 越长成本线性涨。
- **挑战**：historian 与 compaction engine **输入相同（会话跨度）、输出同构（摘要+事实）、
  只是消费方不同（记忆 vs 上下文）**——两条管线各自分块、各自重试、各自诊断。
  一次 LLM 调用产出两种消费者都能吃的结构，成本近乎减半。
- **建议**：列为 C1 之后的第二候选重构；不动契约，纯插件内合并。

### C7. 元机器自重：守卫比在跑的功能多

- **[实测]** 607 用例 + freeze 探测器 + acceptance + records + audit + doctor + 巡检 prompt v5.1，
  守护的功能里 `scoring/evidence-verify(enforce)/force-path 两级/org/machine/collect/review/backfill`
  **默认全关**。判据文本已经腐烂过一次（v5→v5.1 大扫除：7 处"未实现"全是假的）。
- **挑战**：每个新 WP 的流程成本（L1-L5 + 负向对照 + 阶段登记）已经**高于多数 WP 本身的实现**。
  这套纪律对"写用户的记忆库"是正当的；对"纯自有库的功能开关"是过度程序。
- **建议**：分级——**契约写入类**维持全纪律；**自有库纯增量类**降为 单测+阶段门；
  判据一律"出处+口径+当日快照"生成而非手写（已立规矩，执行即可）。

## 3. 如果今天重来：我会删掉的

| 项 | 理由 | 处置 |
|---|---|---|
| S(t) 评分的排序接管 | 唯一消费方（排序）默认关；sidecar 的 health 计数可用一条 SQL 替代 | 冻结，不投新工 |
| evidence-verify 的 enforce 模式 | shadow 都还没跑出有效数据 | 保持 off，判据同 C4 |
| force-path 两级化（publish+drop） | 观察期数据不足 | 保持现状直到溢出真实发生 ≥1 次 |
| org/machine 域 | 前提实测为 0（C4） | C-7 埋点 + 2 周判据，不达标删 |

**不删的**（经得起挑战）：四写入口纪律与纯追加晋升、surface 写入审计、fail-fast+自然重探的 LLM 策略、
freeze 的负向对照方法论（迁移后改用于迁移校验）、route-health 的"易失+流量拥有信号"设计（修 1.1 后）。

## 4. 决策点（按收益排序）

1. **P0 两修**（1.1 路线粒度收紧 + 1.2 ctx_search→ctx_memory）：小、独立、今天可落。
2. **vectorBackfill 开启**（C2：中文正确性事项，走"备份→开→观测"流程）。
3. **C1 迁移演练**（dry-run 全量复制+校验和，产出成本数据后再决定是否收编）。
4. **C4 判据闭环**（C-7 埋点 + C-0 跨会话门 + org/machine 去留日历）。
5. **C5 defer 保底注入**（一天工作量，改善用户可感知的"失忆"）。
